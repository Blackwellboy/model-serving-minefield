# Qwen3.8-27B — RTX 5090 and DGX Spark serving-trap audit

Date: 2026-08-15

This is a sanitized public derivative of the first-party Qwen3.8-27B campaign
run by Blackwellboy across an RTX 5090 and multiple DGX Spark GB10 nodes. The
campaign repository contains machine-specific orchestration and raw receipts;
this note publishes the technical findings that are useful to somebody else
without requiring those private paths or hosts.

The important distinction is deliberate: this is not a model scorecard. It is
an audit of things that looked like model, quantization, runtime or benchmark
failures but were actually narrower deployment or research-stack conditions.

## Finding 1 — MTP support was runtime/build-specific, not model-wide

**Observed.** The Spark NVFP4 lane on aeon-vllm sealed its MTP stage as
`MTP_UNSUPPORTED`. The exact same NVFP4 checkpoint revision was then staged on
a separate Spark with the Drowzeys vLLM development image. That image exposed
Qwen3.5-family MTP support in preflight, and the `MTP1` cell returned the
`BLACKWELL38_READY` canary successfully. The later MTP2 cell was still running
at the captured checkpoint and is not promoted here.

**What this rules out.** `MTP_UNSUPPORTED` on one Qwen3.8 lane is not evidence
that Qwen3.8-27B, the checkpoint, NVFP4, or GB10 cannot use MTP. It establishes
only that the tested runtime/build/path did not support that stage.

**Check.** Pin the exact runtime image/build; inspect model-family MTP support
and accepted speculative configuration; then run the same bounded canary with
MTP off and at depth 1 before making a model-wide statement.

Campaign anchors: `bdac0a864b895fc303561b3a17f1e489e2508d30` and
`ddcbec3da39378b4a7efb9ce09f96569553d0d57`.

## Finding 2 — an amd64 benchmark image failed before Qwen ever ran

**Observed.** A Spark host identified as `aarch64`; the pinned ProgramBench
`task_cleanroom_v6` image identified as `amd64`. Native execution failed with
`exec format error`. No emulation was enabled and the campaign correctly held
the benchmark instead of scoring the model.

**What this rules out.** This failure says nothing about Qwen3.8 capability,
quantization quality or the serving endpoint. The benchmark process never
reached the model.

**Check.** Compare host architecture with every benchmark/helper image before
starting a run. A container being present locally is not proof that the host
can execute it natively.

Campaign anchor: `ddcbec3da39378b4a7efb9ce09f96569553d0d57`.

## Finding 3 — container entrypoint semantics turned `/model` into a CLI command

**Observed.** During the early Drowzeys NVFP4 reproduction, one launch died
with:

```text
Usage: serve [OPTIONS] COMMAND [ARGS]...
Error: No such command '/model'.
```

A corrected launch of the same pinned model and image subsequently returned the
`BLACKWELL38_READY` canary. A separate earlier harness typo produced
`truendocker: command not found`; that is preserved as a runner construction
failure, not combined with the image-entrypoint mechanism.

**What this rules out.** A container that exits before model load because its
ENTRYPOINT/CLI interprets the model path as a subcommand is not evidence that
the checkpoint cannot load.

**Check.** Inspect the image `Entrypoint` and `Cmd`, run its bounded `--help`,
and record the final argv seen by the container. Do not assume a vLLM-derived
image accepts the same `docker run IMAGE /model ...` shape as another vLLM
image.

Campaign anchor: `ddcbec3da39378b4a7efb9ce09f96569553d0d57`.

## Finding 4 — Docker save/load can preserve image content while local image ID differs

**Observed.** The Spark recovery work found that requiring local Docker image
`.Id` to equal the pinned repository digest after `docker save | load` was too
strong. Those are different digest classes: the registry RepoDigest identifies
a registry manifest, while Docker `.Id` identifies image configuration. The
campaign verifier moved to architecture, 46 RootFS layers plus a layer
fingerprint, a pinned aeon version environment value, and GB10/SM121 labels.
That was enough to repair the campaign's immediate false mismatch, but it is
not a complete reusable image-equivalence predicate by itself.

**What this rules out.** `LOCAL_ID != source repo digest` after image transfer
is not by itself proof that the runtime image changed or was corrupted. It also
does **not** mean any image with matching layers and a few selected labels is
safe to treat as identical.

**Check.** Preserve the original registry RepoDigest as provenance and, before
transfer when possible, the source image `.Id`/config digest. After load,
compare like with like: the complete image configuration JSON or config digest
(including `Entrypoint`, `Cmd`, `User`, `WorkingDir`, environment and other
execution-affecting config), plus ordered RootFS/layer identity and
architecture. A difference in executable config or filesystem identity is a
real mismatch; equality between a registry RepoDigest and Docker `.Id` was
never the correct test.

Campaign anchor: `3f57838934dfffb39d535493fc24b9d605ea4219`.

## Finding 5 — a Python telemetry helper crashed the soak at thread join

**Observed.** A Spark BF16 S11 mixed-workload soak became a partial,
non-headline result because `TelemetrySampler` assigned a `threading.Event` to
`self._stop`, shadowing `threading.Thread._stop()`. The failure surfaced when
thread teardown/join reached the inherited internal method, not while model
requests were being served. The field was renamed to `_stop_event` and an
offline regression test was added.

The recovered full BF16 soak then ran for 7,208.5 seconds and recorded 512/512
successful requests, zero server restarts, zero canary failures, and flat
reported VRAM (17,465 MiB start/end). That later run is important because it
separates the harness crash from endpoint health.

**What this rules out.** A long-run worker crash at teardown does not imply the
model server crashed, leaked memory or failed the workload.

**Check.** Preserve the per-request/server telemetry separately from harness
exit status. If a Python `Thread` subclass owns fields named like private
Thread methods (`_stop`, `_delete`, etc.), inspect teardown before blaming the
served model.

Campaign anchors: `3f57838934dfffb39d535493fc24b9d605ea4219` and
`b323dc18f8e9bf3de9505c28155a4fec418ac340`.

## Finding 6 — one decimal canary failure was not enough to call Q4 corruption

**Observed.** On the RTX 5090 Q4_K_M llama.cpp arm, the campaign's decimal
comparison canary returned `9.11` and the stage was conservatively held as a
correctness failure. An immediate rerun on the same pinned model/runtime path
returned `9.9` and passed. The mechanism behind the one-off divergence was not
isolated here.

**What this rules out.** One wrong canary does not by itself establish a
quantization-corruption mechanism. The failed transcript is real; the causal
label remains open because the next exact campaign check did not reproduce it.

**Check.** Preserve the exact provider-bound request, effective sampling
settings and raw response, then repeat the same canary enough times to measure
whether the failure is deterministic. Only call quantization corruption when
a quant-specific A/B or other direct evidence localizes it.

Campaign anchors: `1338b3518a6590b0ae8e6198b1edcb0437736de8` and
`d68774e4f0615cc48aa94bad163532c1cc6dae5e`.

## Things we deliberately did not turn into traps

- **Vision unsupported** on the text baseline is a capability/non-applicability
  result, not a serving failure.
- **SGLang code present** on an arm64 nightly image is not a model result when
  the exact checkpoint was not staged and inference never started.
- A stage-level `PASS` or `HOLD` is not automatically a model-quality verdict;
  the evidence beneath the stage has to say what actually ran.
- The Drowzeys MTP2/MTP3 cells are not claimed from the early checkpoint. Only
  the completed MTP1 canary is used above.

## Public Minefield disposition

These findings are useful immediately but several are research-stack/runtime
lessons rather than Qwen-specific model defects. They are therefore published
as L-series leads first and routed from the Qwen3.8-27B model page. Promotion
to a canonical trap should happen when the mechanism has the same level of
bounded evidence and stable ownership expected of the canonical registry.
